# Última Milha — contexto do projeto

Plataforma de gestão de operações de entregas de última milha. Mobile-first, multi-tenant, sempre online, PWA.
React + Vite + Tailwind 4 · Supabase (Postgres + Auth + RLS + Edge Functions) · react-i18next (PT/EN) · EUR apenas (v1).
Supabase: projeto **ERP Last Mile** (`<SUPABASE_PROJECT_REF>`). Na mesma conta existem ERP Energy e ERP_Trading: **nunca lhes tocar.**

## Comandos
- `npm run dev` · `npm run build` · `npm run typecheck`
- `npm run test:db` (PGlite, regras/RLS) · `npm test` (unitários + i18n) · `npm run check:real` (projeto real)
- `npm run test:ui` / `npm run test:ui:accounting` / `npm run test:ui:transition` (Chrome headless; precisam de `npm run dev -- --port 5199`)
- `npx supabase db push` aplica `supabase/migrations/*.sql` · `npm run seed` recria os dados de exemplo
- Utilizadores de teste: `node scripts/test-user.mjs <email> <pw> <papeis> [--ops …] [--new-tenant …]`

## Regras não-negociáveis (têm de estar sempre verdadeiras)
1. **Isolamento (RLS na BD, não só no código):** Rotas e Registos isolados por Operação; **Viaturas e Motoristas partilhados ao nível do Tenant** (exceção deliberada — não "corrigir"); Contabilidade transversal ao Tenant.
2. **Integridade histórica de preços:** a receita de um registo diário é calculada no servidor com o tarifário em vigor **na data do registo** (`tariff_snapshots`) e gravada; mudar o tarifário **nunca** recalcula registos existentes.
3. **Nunca apagar fisicamente** nada (DELETE bloqueado por trigger; `audit_log` imutável). Soft delete (`deleted_at`) com audit trail (quem, quando, antes/depois). Nos movimentos o motivo (`motivo_apagado`) é obrigatório e só o Super Admin apaga.
4. **Nenhum campo obrigatório no registo diário**, exceto rota + data. Um registo por rota+data.
5. **Sem texto hardcoded** (tudo em `src/i18n/{pt,en}.json`) e **sem hex nas componentes** (tokens em `src/index.css`).

## Permissões
Super Admin: tudo. Gestor: operações atribuídas, valida registos, **sem Contabilidade**. Operador: cria/edita registos, nunca apaga, sem definições/tarifário. Motorista: só o seu ecrã de registo e só enquanto não Validado. Contabilista: só Contabilidade. Auditor: só leitura nas áreas atribuídas (Contabilidade só com `accounting_read`).
Convites: Super Admin convida qualquer papel; Gestor só Operador/Motorista nas suas operações.

## Registo diário
Estados Rascunho → Submetido → Validado (só Gestor/Super Admin validam). **Um registo Submetido/Validado nunca volta a Rascunho** (transição inválida, recusada no servidor). Editar um Validado devolve-o a Submetido e notifica quem validou; **anexar-lhe uma alocação de fundos (propagação) faz o mesmo** (reverte para Submetido e notifica quem validou). O rascunho grava sozinho (servidor). `validado_por`/`validado_em` só o servidor escreve (validar define-os, reabrir limpa-os; enviá-los num UPDATE é ignorado).

## Contabilidade — regras de negócio
- **Estado inicial (decidido pelo servidor; o cliente não o escolhe):** alocação de fundos → sempre **Pendente**; lançamento automático **acima** do limite (`accounting_settings.validation_threshold`, defeito 100 €, só o Super Admin altera) → Pendente, igual ou abaixo → Confirmado; lançamento manual → Confirmado.
- **Lançamentos automáticos só a partir de Submetido:** o combustível e as portagens de um registo diário só geram lançamento (origem Automático) quando o registo **sai de Rascunho** (Submetido ou Validado). Um registo em Rascunho **não gera nenhum**, porque o rascunho grava automaticamente enquanto se escreve e criaria uma versão por cada gravação. Se o registo é apagado, ou o custo fica a 0/vazio, o lançamento ativo é apagado (soft delete, com motivo).
- **Versionamento:** editar o custo de um registo que já gerou lançamento **não atualiza** o lançamento: cria um novo (`versao_anterior_id`), e o antigo fica soft-deleted com motivo "substituído por edição". Só o ativo mais recente conta nos totais. A nova versão volta a aplicar a regra do limite (nunca herda a validação).
- **A origem (Automático / Manual-Rota / Manual-Geral) é decidida pelo servidor, nunca pelo utilizador:** o cliente não a envia (enviá-la ou alterá-la é recusado); num manual acompanha a operação (com operação = Manual-Rota, sem = Manual-Geral); `automatico` só o cria o sistema a partir do registo diário. Nada de `origem` em formulários/API.
- **Referências coerentes:** conta, operação, rota, motorista, lançamento de referência e registo de um lançamento (e viatura/motoristas de um registo diário) têm de ser do mesmo Tenant; a rota tem de pertencer à operação do lançamento. Imposto por trigger (`app.movements_refs`, `app.records_refs`).
- **Um lançamento automático só muda no registo diário.** Na Contabilidade só se pode validar/reverter, reclassificar rota/operação, atribuir conta e editar a descrição; **todos os outros campos são imutáveis** (imposto por trigger: valor, data, tipo, subcategoria, pessoa, lançamento de referência…). `created_by`/`created_at` de um lançamento só o servidor os define; `motivo_apagado` só se define ao apagar (nunca numa linha ativa). No Quadro, arrastos consecutivos do mesmo cartão correm em série (um PATCH de cada vez). Sem conta por defeito (`default_account_id`) o automático nasce com `conta_id` nulo.
- **Totais/saldo oficiais só contam Confirmado.** Pendentes aparecem sempre à parte ("€X por validar"), nunca somados ao saldo. Pendente = contorno vermelho (`.pending-outline`) em qualquer vista: escuro 1.5px #ef4444; **claro 2px #dc2626 com glow de 4px** (tokens `--pending-*`); glow com pulso lento (1.8 s) — a **única animação em loop da app**, desligada com `prefers-reduced-motion`.
- **Distribuição de fundos:** transferência (Débito com `pessoa_responsavel`) + alocações filhas (`lancamento_referencia_id`). O detalhe mostra alocado vs recebido; sobre/sub-alocação nunca ficam escondidas. Só alocações a **débito** contam para o alocado. A sobre-alocação **não é bloqueada** mas é sinalizada **no servidor** (vista `fund_transfer_status` + notificação `fund_over_allocated` a Super Admin e Contabilistas quando o excesso agrava), não só na UI; para bloquear basta um `raise exception` em `app.movements_overalloc()`.
- **Propagação diferida:** uma alocação com operação+rota gera uma linha de custo no registo diário dessa rota+data **se o registo já existir**; se não, fica "por ligar" (`registo_id` nulo) e anexa-se quando o registo for criado. Nunca cria o registo. A linha de custo é uma cópia inicial: depois editam-se de forma independente (editar valor/descrição de um lado não mexe no outro). **Exceção deliberada:** mudar a rota, a data ou o **tipo** (débito→crédito; mudar só a operação não conta) de uma alocação **já propagada** (com `registo_id`), ou **apagá-la** (soft delete), apaga (soft delete) a linha do registo antigo, devolve a Submetido um registo Validado e avisa quem validou, e (ao mudar rota/data) liga a alocação ao registo da nova rota+data se existir (senão volta a "por ligar"). A UI pede confirmação antes — também quando uma alocação ainda por ligar vai ligar-se a um registo **Validado** (que voltaria a Submetido).
- **"Por ligar" e "Sem registo previsto":** a vista **Por ligar** lista as alocações (operação+rota, a débito, sem registo diário) mais antigas primeiro; a Contabilidade nunca cria o registo. Uma alocação = **uma linha de custo ativa** (índice único parcial em `daily_record_costs.movimento_id`; ligações concorrentes não duplicam). `app.system_write` repõe sempre o valor anterior (nunca `'0'` fixo). O Contabilista/Super Admin pode marcar uma alocação como **Sem registo previsto** (`movements.sem_registo_previsto`; só numa alocação realmente por ligar; reversível; audit): deixa de alertar e sai de "Por ligar" (fica numa secção própria); volta a "por ligar" se mudar a rota ou a data, e a marca é **limpa quando o registo aparece e a alocação se liga** ("não me avises": ligar-se continua a acontecer). **Sem timeout automático.** O alerta `allocation_unlinked` ignora rotas apagadas e as marcadas.
- **Validar:** só Contabilista/Super Admin (fica `validado_por`/`validado_em` + audit). Reclassificar (rota/operação) uma alocação validada **mantém** a validação; mudar valor, tipo, data ou pessoa tira-a.
- **Notificações:** sempre que um lançamento entra em Pendente, notifica **todos** os Super Admin **e** todos os Contabilistas do tenant (push incluído), no máximo **uma vez por movimento, dia e valor** (reverter/revalidar o mesmo valor no mesmo dia não repete; corrigir o valor avisa de novo). Não há resumo diário. "Pedir correção ao Gestor" (detalhe de um automático, `public.request_cost_correction`) notifica os Super Admin e os Gestores da operação (`auto_cost_disputed`), no máximo uma vez por movimento e dia (`request_cost_correction` devolve o nº de avisados; **-1 = ninguém a avisar**, **0 = já pedido hoje**); a notificação leva a rota/data do **registo de origem** (o automático pode ter sido reclassificado; o Contabilista vê-a via `movement_origin_record`, pois não lê `daily_records`); o automático continua a só mudar no registo diário.
- **Etiqueta da linha de custo propagada:** "Pagamento distribuído — <pessoa>" (travessão). Uma alocação cuja transferência foi apagada mostra "Origem: transferência removida" e mantém-se visível (Distribuições, "Alocações sem transferência ativa").
- **Operação selecionada na Contabilidade:** os totais, Lista, Agrupado e Quadro mostram **só** movimentos dessa operação — as despesas soltas (sem operação) não entram (como no dashboard). Exceção deliberada: a fila "Por validar", o cartão "por validar" e as Distribuições incluem também o que não tem operação, para nunca esconderem um pendente nem uma transferência.
- **Trabalho em lote e filtros:** na Lista e na fila "Por validar" (só Contabilista/Super Admin) há seleção múltipla com "Validar (N)" e "Atribuir conta" (um PATCH por bloco de 100; o servidor continua a decidir e a registar cada movimento). O filtro de conta tem "Sem conta" (movimentos, sobretudo automáticos, sem `conta_id`); a linha "Sem conta" do painel Contas leva a ele. Cada Pendente mostra **porquê** (alocação de fundos / automático acima do limite / revertido a pendente). **Carregamento por páginas** (o PostgREST devolve no máximo 1000 linhas por pedido; um `.limit(3000)` sozinho truncava em silêncio): a Contabilidade carrega movimentos até um teto de 10 000 e o dashboard registos diários até 20 000; se o teto for atingido aparece um aviso (e o Excel exportado sai como `…_PARCIAL.xlsx` com uma folha «Aviso») «Só se mostram os N de M… totais INCOMPLETOS». Agregação no servidor fica para depois. Para isto aguentar milhares de linhas: a policy `mov_select` usa `(select app.tenant_id())`/`(select app.can_read_accounting())` (avaliadas uma vez; por linha custavam ~0,4 ms e estouravam o `statement_timeout` de 8 s) e há um índice parcial `movements_active_order`; o `count` exato só se pede no 1.º pedido. O mesmo vale para `daily_records`/`daily_record_costs` (0022): a condição depende da linha (`route_id`), por isso a policy usa `route_id in (select app.readable_routes())` (conjunto de rotas legíveis calculado uma vez; ~0,8 ms/linha antes), com o ramo do Motorista; a visibilidade por papel está provada por um teste-oráculo em SQL. O `audit_log` (append-only, cresce com cada escrita) segue a mesma regra (0023: `(select app.tenant_id())`/`(select app.has_role(...))`; 1885 ms → 12 ms com ~62 000 linhas). Medido no projeto real: `daily_records` 1342 → 66 ms; consulta tipo dashboard 866 → 136 ms. **Regra para policies novas:** funções sem argumentos de linha (`app.tenant_id()`, `app.has_role(...)`, `auth.uid()`) escrevem-se como `(select ...)`.
- **Renderização por blocos:** Lista, fila, Agrupado (por grupo) e Quadro (por célula) desenham **100 cartões de cada vez** ("Mostrar mais"); um dia fechado do Agrupado não monta cartões. Só é visual: totais, "Selecionar todos (N)", lote, exportação e a fila usam a lista **completa** (antes: Lista 9,7 s com 3627 movimentos e 22,8 s com 10 000; agora ~0,3 s e ~1,7 s).
- **Vistas:** Lista, Por validar (fila de qualquer pendente), Agrupado (dia → rota/"Geral", cada movimento uma só vez), Quadro (linhas = rotas + Geral; colunas Pendente|Confirmado; arrastar coluna = validar, linha = reclassificar, diagonal = ambos numa só atualização/audit; em toque, bottom sheet).
- **Export:** `Contabilidade_AAAA-MM-DD.xlsx` — Data, Conta, Tipo, Valor, Categoria/Origem, Rota, Estado, Origem (Automático/Manual), Descrição, Pessoa responsável, Subcategoria. Exporta o que se está a ver (Lista/Agrupado/Quadro = filtrado; Por validar = a fila; Por ligar = as por ligar + as sem registo previsto; Distribuições = transferências + as suas alocações + as alocações sem transferência ativa; Contas = tudo).

## Outras decisões de desenho
- **Transição de entrada (login → app):** só em arranque **frio** (login manual, ou abrir a app com sessão guardada) — nunca ao navegar dentro da app. Fase 1: o cartão de login encolhe/desvanece; fase 2: ecrã com círculo neumórfico e 4 ícones a alternar (camião, caixa, rota, check) + «A preparar a tua operação…»; fase 3: a app entra com fade + subida de 16 px. Tudo em `src/lib/entryTransition.ts` (`ENTRY`: durações, `showLabel` para remover o texto), `src/components/EntryTransition.tsx` e `.entry-*` em `src/index.css`. **Só `transform`/`opacity`**; cores por tokens (`--accent`=`--brand`, `--bg-surface`=`--bg`, `--shadow-neu` com `--neu-hi/--neu-lo` por tema). Com `prefers-reduced-motion: reduce` nada disto monta (vai direto à app). Em navegador automatizado (`navigator.webdriver`) salta, para os outros testes E2E não esperarem ~1 s por login, salvo `localStorage['um.entry']='force'` (usado por `test:ui:transition`). O `AuthProvider` expõe `profileReady` (perfil carregado para a sessão atual), para não mostrar «sem perfil» logo a seguir ao login.
- Custos fixos (salários, "outros") e custos de viatura (IUC, seguro, manutenção, aluguer mensal) rateiam-se por `/30` por dia; ficam de fora da margem quando o dashboard tem filtro de rota/motorista/viatura.
- Escalões de km são progressivos (€/km por fatia de km).
- **Tarifário versionado:** cada mudança é o seu próprio snapshot (`tariff_snapshots`, ordenado por `valid_from`+`versao`), incluindo várias no mesmo dia; snapshots são imutáveis; um registo usa o último snapshot em vigor na sua data.
- **Postos de frota — intervalos com fim EXCLUSIVO:** `slot_assignments.data_fim` é o dia em que a viatura **já não** está no posto (não o último dia em que esteve); numa troca A→B no dia D, A.data_fim = D = B.data_inicio (sem sobreposição nem buracos); `data_fim` nulo = ainda lá. Um posto tem no máximo uma viatura aberta e uma viatura no máximo um posto (índices únicos); atribuir a um posto ocupado substitui a anterior. Viatura apagada, **Vendida** ou **Em manutenção** liberta o posto (não regressa sozinha ao voltar a Ativa; `devolvida` não liberta — por decidir).
- Só Gestor/Super Admin apagam (soft delete) registos diários; Operador/Motorista não, nem pela API.
- Alertas diários (`pg_cron`, 20:00 UTC): registo em falta, fundos por reconciliar (7+ dias; só alocações a débito contam), alocações "por ligar ao operacional" há 3+ dias (semanal, ao Gestor da operação e ao Contabilista; `allocation_unlinked`), margem negativa do mês fechado, custos a vencer. Push por Edge Function `send-push` via `pg_net`.
- O relatório PDF é uma página imprimível (`/relatorio`) + "Guardar como PDF" do browser.

## Agente de testes
`.claude/agents/ultima-milha-tester.md` valida estas regras contra o projeto real. Só pode escrever em `qa/`; a fronteira é **imposta** pelo hook `.claude/hooks/qa-write-guard.mjs` (testes: `node --test .claude/hooks/qa-write-guard.test.mjs`). Se mudares regras aqui, atualiza também o agente.
`.claude/agents/ultima-milha-contabilidade-tester.md` é o par focado só na Contabilidade (31 casos: fundos, versionamento, validação seletiva, Agrupado, Quadro); mesma guarda de escrita. Se mudares regras da Contabilidade, atualiza-o também.
`.claude/agents/ultima-milha-contabilidade-analista.md` (Opus, só leitura) não testa: analisa a usabilidade da Contabilidade e devolve um relatório de exceções mal tratadas e simplificações; não implementa nada. Também tem uma secção de regras decididas ("não são achados") — mantém-na alinhada com este ficheiro.
